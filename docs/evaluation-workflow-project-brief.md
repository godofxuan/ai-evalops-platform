# 本轮项目价值、讲解与使用起点

## 一句话

AI EvalOps 是评测执行与证据管理后端：把同一批任务交给两个版本，可靠保存执行过程与结果，再让开发者检查差异、解释失败并复测。它不是新大模型，也不自动让 Agent 变聪明。

## 本轮真正补上的能力

此前已有执行、持久化、门禁和证据合同；本轮把这些能力变成可操作的流程：一个命令演示或运行配置，逐题看答案与评分原因，关联受限 OTLP 轨迹，导出盲审材料，对照实际标注，再用完整原题集回归。另将固定重复运行整理为可恢复的可靠性面板，避免一个平均分掩盖不同题目的稳定性。

这是对成熟开源项目设计的学习，不是声称已经达到 Langfuse、Phoenix、Promptfoo 或 DeepEval 的生态成熟度。没有新建前端服务，没有安装新的 Agent 框架，没有付费 judge；先使用原有锁定依赖与开放数据合同。

## 能体现哪些理解

1. **执行正确不等于回答正确。** 队列/重试成功、工具选择正确、答案匹配是不同问题；诊断评分不会覆盖原有质量门禁。严格 JSON 结构相同不等于业务语义正确，非法参考答案也不能记为候选答错。
2. **高分不一定可信。** 原始题集、观察、配置与报告需能离线重建；哈希只保证内容一致，不能证明数据来源真实。缺失与失败不能从分母消失，未知成本不能补零。
3. **稳定性不只是平均分。** 固定多次执行按题汇总成功次数；经验 any/all 不冒充无偏 pass@k，重试后的流程成功率不冒充模型单次成功率。没有独立采样证据就不作相应推断。
4. **可观测不等于知道根因。** 轨迹可说明报告了哪些步骤、耗时和错误，不能单凭 span 结构推断任务已完成。缺失父节点和复用 trace ID 必须显式表示。
5. **评测要能进入下一次开发。** 失败重点与完整回归题集同时导出；只挑失败题、改 gold、降低门槛或反复挑最好成绩都不能证明总体提升。
6. **工具的操作错误也有成本。** 输出路径不合法应在发请求前拒绝；执行后磁盘/分析失败应保留结果供离线恢复，而不是建议重新花钱调用目标。

## 可用于简历的克制表述

> 基于 Python 构建多租户异步 AI 评测后端，扩展声明式 A/B 执行、解释性诊断、受限 OTLP 轨迹关联、盲审校准及完整题集回归流程；实现可重算私有证据包与执行后离线恢复，并增加固定重复运行的可靠性分析。通过真实回环 HTTP 反例修复输出预检时序问题，将无效输出条件下的不必要目标请求由 4 次降为 0 次。本轮全量非集成回归 1401 项通过；数据库集成及真实业务/人工质量验收明确分列。

“4 到 0”只描述已覆盖的本地反例，不是吞吐提升或生产费用统计。1401 是整库通过数，不是本轮新增测试数。没有真实用户量、生产 QPS、业务 A/B 提升或人评一致率，简历不得补写这些数值。

## 面试时如何回答

**为什么不用现有平台？** 生产选型会优先比较成熟方案；本项目重点展示多租户执行正确性、证据重算、失败恢复和评测有效性边界。借鉴开放协议与工作流，避免自行发明另一套 Agent 框架。

**如何证明效果？** 当前可证明软件路径与合同：真实 fixture 运行、回环 HTTP、导出、离线重算、恢复与反例回归。不能凭这些证明模型更好。后者还需要合法真实数据、固定两版应用、预先门槛及实际独立标注。

**为什么不直接用 LLM 打分？** 增加 judge 会引入成本、波动、偏好和版本问题。先把参考有效性、评分适用范围、盲审输入和校准统计做好，再决定是否接入固定版本 judge。本轮没有把合成标签写成人工验收。

**什么没有完成？** 新分支远端 CI、真实 PostgreSQL 集成、Phoenix/Langfuse 服务端联调、真实业务 A/B 和真实人工标注均不能声称已通过。功能已经冻结，不以继续堆功能掩盖这些外部条件。

## 最短学习路线

先按 [使用说明](evaluation-workflow.md) 运行 Agent demo，打开逐题 HTML；选择一条 baseline 有发现的题，核对具体工具指标及答案；再执行 regressions，对照原题集哈希；最后看 [执行记录](reviews/evaluation-workflow-execution.md) 中的失败、修复与未验收边界。

不要从几十份历史报告开始阅读。新的入口是仓库根目录 `EVALUATION_WORKFLOW.md`；历史 README 因证据冻结未重写。
