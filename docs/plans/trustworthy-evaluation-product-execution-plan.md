## 1. 目标、边界与完成定义

### 1.1 要解决的实际问题

让使用者能够提交一个 QA 或 Agent 工具调用实验，平台保存版本与输入身份，可靠执行两组任务，在中断后恢复，输出有明确缺失项和指标解释的报告，并让命令行准确反映门禁是否通过。

这一轮不是创建另一个 RAG 项目，也不是把两个仓库合成一个仓库。RAG 只是可接入的被测服务之一。工程测试可使用自有、确定性的 HTTP Agent 服务，不以付费模型或 RAG 新分支完成为前置条件。

### 1.2 必须完成的范围

- 修复 R1：FORMAL 资格和前置检查不能硬编码 PASS。
- 修复 R2：HTTP Agent 执行轨迹、终态、错误、预算信息完整进入评分。
- 修复 R3：质量 FAIL 必须产生非零 CLI 退出码。
- 修复 R4：聚合合同增加版本化语义与受限内容结构验证。
- 修复 R5：未知成本、引用指标、缺失测量的语义正确。
- 修复 R6：产品实验入口接入现有持久 Run/Job，完成中断恢复与报告导出。
- 修复 R7：证据包必须满足其结果状态所要求的完整性。
- 修复 R8：区分基础设施异常、程序错误与被测质量失败，保留安全原因码。
- 修复 R9：隔离目标服务的任务输入与评测答案/标签，避免 metadata 转发污染评测。
- 修复 R10：为 product 输入、HTTP 响应、任务窗口和总时间建立资源边界。
- 修复 R11：区分实验名称、固定内容、一次执行、幂等重放和 attempt 身份。
- 改进 R12：分别表达绝对达标和配对不退化，平衡执行顺序，补可解释的切片报告。
- 修复 R13：支持明确禁止工具调用的合法 Agent case，增加微型安全回归集。
- 补充 R5：工具参数比较区分 JSON bool/number，不把 1 与 true 当成同一个参数。
- 提供一条从提交到报告的可运行示例、清晰 README、逐阶段学习记录和证据索引。

### 1.3 本轮不包含

- 不承诺模型质量提升、正式人评完成、Shadow PASS 或 production-ready。
- 不购买模型调用，不索取或公开私有样本、令牌、原始商业数据。
- 不改 RAG 仓库，不为通过验证重写旧证据或替换历史 SHA。
- 不重写调度器、不引入第二套队列、不引入 Kubernetes 或新前端大工程。
- 不删除分支、不 force push、不自动合并 main、不改变仓库默认分支或破坏现有简历链接。
- 不以“测试数量增长”或“CI 变绿”代替正确性验收。

### 1.4 三类结论必须分开

| 结论 | 本轮完成依据 | 可否因本轮工程通过自动获得 |
| --- | --- | --- |
| 工程修复完成 | 缺陷回归、真实服务集成、中断恢复、版本与证据一致 | 可以，但必须逐项验收 |
| 正式质量结论 | 合格来源、预先固定协议、足够真实样本、对应人审等 | 不可以 |
| 生产部署资格 | 权限、规模、容量、运维、安全等独立验收 | 不可以 |

正式输入不足时，正确输出 INPUT_REQUIRED 本身可以是工程验收通过的证据；不能为了让所有业务状态显示 PASS 而降低要求。

## 2. 执行方法与阶段关卡

按 S0 → S1 → S2 → S3 → S4 → S5 → S6 → S7 执行。前一阶段的关卡不通过，不用下一阶段的功能掩盖问题。

| 阶段 | 核心交付 | 相对工作量/风险 | 进入下一阶段的条件 |
| --- | --- | --- | --- |
| S0 | 固定基线、复现矩阵、版本与状态合同 | 小/低 | 已知问题能复现，目标语义明确 |
| S1 | 输入输出隔离、错误分类、限额、身份、退出码 | 中/中高 | 不泄漏标签、不吞错误、执行有界、FAIL 非零 |
| S2 | 资格、指标、无工具用例、配对门禁和顺序 | 中/中高 | 缺失不获 PASS，达标不冒充不退化 |
| S3 | 聚合合同与实验包严格校验 | 中/中 | 错 schema、错题数、缺 arm 被拒绝 |
| S4 | 持久实验关联、API/CLI、共享评分路径 | 大/高 | 实验真实使用现有 Run/Job |
| S5 | 故障恢复、并发与隔离、完整 CI | 大/高 | 故障矩阵和真实进程测试通过 |
| S6 | 使用文档、教学记录、简历证据说明 | 中/低 | 从干净环境能按文档运行 |
| S7 | 精确版本验证、条件性发布、跨任务同步 | 中/外部依赖 | 本地/远端/CI/证据对应且无遗留改动 |

工作量是排序依据，不是时长承诺。S4 的事务接入与 S5 的进程故障验证通常需要最多判断；S0 完成后根据实际环境重新估算，不用猜测一个保证完成日期。

执行时采用小改动循环：说明假设 → 写覆盖该行为的失败测试 → 确認失败原因符合预期 → 最小实现 → 定向回归 → 相关集成 → 记录结果。禁止先大面积重构再寻找通过理由。

### 2.2 分批交付与停止条件

- 交付 A（S0–S3）：可信性修复包，优先修已复现错误与标签/资源边界；local 路径可独立验证。
- 交付 B（S4–S5）：API→worker→中断恢复→报告的一条真实持久流程，不新增第二调度器或 UI 大工程。
- 交付 C（S6–S7）：文档、教学、简历事实、精确 SHA/CI 和同步回执；必须依赖实际 A/B 工程交付证据，这里的 A/B 是交付批次，不是正式质量试验。
- 后续 T1–T4 见第 13 节，仅按具体需求触发，不作为本轮隐藏阻塞项。

默认按 A→B→C 推进。数据库环境不可用时先做安全可执行部分，集成标为阻塞；正式模型 A/B 输入不足不阻塞工程修复。

## 3. S0：固定基线与合同设计

### 3.1 基线检查

1. 检查当前分支、完整 HEAD、Git 状态、worktree 和远端。若用户有未提交修改，保留并划清范围，不 reset、不覆盖。
2. 获准开始实现后，再创建 `codex/trustworthy-evaluation-product-v2`。基点采用重新核实后的目标主线；若与审查基线不同，先审查差异。分支若已存在，先检查是否为同一轮工作，不重建或覆盖。
3. 检查 Python 3.12、锁文件、PostgreSQL/Redis/MinIO、可用 Docker 环境与端口。测试只使用隔离数据/服务，不默认借用用户已有数据库。
4. 把忽略目录中的审查发现摘要和复现方式纳入新的受版本控制执行记录；不要提交临时探针或含机器私密路径的运行日志。
5. 重跑定向基线、当前证据校验，记录通过、失败、跳过及原因。原有失败与新引入失败分开。

### 3.2 先固定几个决定，避免中途反复改接口

- 一个结果至少分别表达：执行状态、测量完整性、自动质量判断、人审状态、正式声明权限。不能用一个 PASS 混合表达全部含义。
- 新的输出/指标语义采用显式版本。现有 v1 文件按其原版本读取；新实现不悄悄重新解释旧 citation_correctness 或旧 cost=0。
- 现有 `FormalCaseMeasurement` 的 cost 为必填 float，且统计直接使用该字段。不能只在 provider 里改为 None 后把缺失补回 0。新产品观测先采用版本化测量模型，满足完整性后才进入相应的正式统计适配器。
- 旧结果可以标为 legacy/未验证语义，不因为能读取就获得新等级背书。旧文件不改字节、不重新签署成新证据。
- 冻结 QA 和 AGENT_TOOL_USE 各自的必需字段、必需指标与不适用指标。Agent 的引用指标不能凭空写成 1.0。
- 固定 policy、spec、dataset、target/evaluator 版本/配置摘要和随机种子。执行过程中更改 policy 必须形成新实验身份。
- 先复用 `app/agent_eval/schema.py` 已有 AgentRunArtifact。HTTP 层采用版本化适配或明确理由的精简投影，记录终态/轨迹映射与信息损失，不造第三套互不兼容的模型。
- R11：experiment label 是名称，content identity 固定内容，execution_id 标识一次运行。恢复保留 execution，重新运行产生新 execution；同次提交幂等重放，真正 retry 使用新 attempt。durable 复用真实 Run/Job/attempt，local 使用同一语义，不单凭 label 生成全部身份。
- R9：明确 task input/public context 与 evaluation-only labels/fixture profiles 分区。保存在评测端的数据不等于允许转发给被测服务。

## 4. S1：先修真实 HTTP 输入与 CLI 失败传播

涉及现有文件：`app/product_experiments/spec.py`、`runner.py`、`app/domain/evaluation.py`、`app/targets/http_rag.py`、`scripts/run_product_experiment.py`、产品和 target 单元测试。新合同模块文件名在实现前按现有结构确定。

### 4.1 HTTP Agent 合同与映射（R2）

1. 区分 QA response 与 Agent response。保留兼容的 QA 映射，不要求普通 QA 伪造工具调用。
2. Agent 合同明确包括：schema 版本、trace/execution 身份、终态、工具调用及参数/状态、工具错误、预算状态、耗时与成本来源、被测版本声明。
3. 明确 `tool_calls=[]` 表示已观测到零次调用，字段缺失表示未提供证据，两者不同。
4. 终态、布尔和数值严格校验；拒绝用 bool 冒充数值、NaN/Infinity、负耗时/费用、错误 enum 和超长/过大 payload。
5. 统一输入归一化函数，fixture、HTTP、后续 worker 都调用同一合同；不复制第二套评分前转换。
6. 工具恢复后最终 completed 可以成立；但历史工具 error 仍需保留。明确统计的是“至少一次错误的 case”还是“错误调用比例”，并写入指标版本。
7. 服务报告耗时与客户端观测耗时分开。timeout、解析失败、transport error 记录真实失败类别，不伪造成 completed 或工具 error 的替代事实。
8. 版本身份至少区分 expected、observed、自报/独立绑定的可信程度。返回一个匹配 SHA 的字符串不是密码学来源证明。
9. 日志和报告先脱敏，不把 Authorization、auth 环境变量值或任意原始 trace 自动公开。

### 4.2 CLI 状态与退出码（R3）

推荐保留默认自动检查语义，并新增明确的正式门禁选择（参数名建议 `--gate automated|formal`，需在 S0 固定）。

| 结果/条件 | 自动门禁 | 正式门禁 | 说明 |
| --- | --- | --- | --- |
| DEMO_PASS | 0 | 2 | demo 不具备正式资格 |
| 自动 PASS、人审 pending | 0 | 2 | 自动通过不等于正式通过 |
| DEMO_FAIL / AUTOMATED_FAIL | 1 | 1 | 明确质量失败 |
| 缺输入/测量不足/所选门禁仍待定 | 2 | 2 | 无法给出所选门禁通过结论 |
| 内部异常/产物导出失败 | 3 | 3 | 工具执行失败，不是质量结论 |
| 用户中断 | 130 | 130 | 明确记录中断；不得伪造 PASS |

本轮不新增“人审已经通过”的捷径，也不解除 `formal_quality_claim_allowed=false` 的现有边界。未来若接入正式批准流程，必须另有合同。

实现要点：集中式映射、穷尽状态检查、未知状态非零；可生成的失败诊断仍导出；产物导出失败不能被原有 PASS 覆盖。轮询超时需说明服务端任务仍在执行，不能把客户端超时解释为服务端已取消。

### 4.3 测试与验收

实施前先完成下列三个补充工作包；它们与 R2/R3 共用合同、日志和测试，不独立搭建新系统。

**S1-A：输入隔离与 preflight（R9）。**

1. 新请求投影只读取显式允许的 task input/public context，不复制整个 metadata。
2. reference answer、expected calls、fixture profile 与 evaluation-only 嵌套字段都不发送；不能只依赖字段名黑名单。
3. 确需上下文的任务使用固定映射；记录映射版本与请求摘要，公开日志不存完整敏感请求。
4. 旧 include_metadata=true 配置遇到不明确整包转发时阻断并提示迁移；默认关闭的旧 QA 保持行为。
5. 增加 validate/preflight 入口（命名在 S0 固定，当前尚不存在），列出题数、规则、限额、将发送的字段名称和缺输入。默认不调用目标、不创建 Run、不读出密钥值；网络探测是独立显式选项。

**S1-B：失败分类和执行身份（R8/R11）。**

1. 复用既有 classify_failure，记录安全 error_code、阶段、HTTP 状态、retryable 与关联 ID，不把所有异常写成 tool_error。
2. 合法响应中的差答案/工具错误是有效质量观测，未得到合法响应是执行失败/缺测；内部程序错误不作为差答案继续跑正式统计。
3. 不在公开产物输出原始异常全文。受控日志按 execution/attempt 排查，合成秘密标记必须脱敏。
4. local 创建/恢复使用 S0 身份规则；同名新输入/新执行不复用旧 ID，重试 attempt 变化。不得假定外部服务识别 X-EvalOps-Job-ID 就保证幂等。

**S1-C：资源有界（R10）。**

1. 限制输入字节/题数、单 case/轨迹/调用尺寸、HTTP 解压后字节数。优先复用核心限额，缺项再增；默认值由样例与合理安全预算确定，不冒充实测容量。
2. HTTP 增量读取，超限立即关闭。Content-Length 只预检，chunked/无长度也计数；压缩响应需评估解压瞬时内存，不能等 aread 全量结束后检查。
3. local 总 case deadline 覆盖 DNS/连接/读取/解析，支持实验 deadline/取消；durable 保留现有 worker 总 timeout。
4. 有界窗口替代一次为所有 cases 创建 gather tasks；Semaphore 只代表并发限制，不代表内存上限。
5. 记录两组、重复与最大重试对应的计划调用数，限制总尝试数。费用未知或没有可靠预算预留时，不承诺硬美元成本上限。
6. HTTP client 生命周期明确关闭；连接复用若改动必须保持 DNS/peer/目标凭据隔离，不为了性能移除安全检查。

补充测试要求：实际构建/发出的请求无 gold 标记而公共上下文仍存在；timeout/401/429/5xx/非法 JSON/内部异常/合法差答案可区分；阈值内与阈值+1、慢流总 deadline、取消关闭和任务窗口有界；新执行/幂等重放/retry 身份分别成立。测试用受限合成流，不做内存耗尽试验。

- 用真实 `_HTTPProvider` 归一化逻辑覆盖 completed、工具错误、预算耗尽、缺轨迹、错误终态、无工具任务。
- 合成 HTTP 响应映射后的每个关键字段与评分结果逐项断言，而非仅检查 HTTP 200。
- CLI 映射单元测试覆盖全部状态；使用真正子进程验证至少一个自然产生的 DEMO_FAIL，退出码必须为 1。不能只有 mock `_run` 的测试。
- CI 的“负面测试”捕获并断言预期非零，不能用 `|| true` 掩盖其他错误；真正质量门禁步骤则应让非零直接失败。
- 原有 QA demo、target SSRF 测试、其他 CLI 行为继续通过。

S1 停止条件：仍丢失执行信息、缺字段默认为健康或任意质量 FAIL 返回 0，均不得标完成。

## 5. S2：正式资格、未知值与评分语义

涉及：product spec/runner/evaluators/report、`app/external_harness/formal_quality.py` 与 quality gate、相应 policy/spec 版本及测试。

### 5.1 正式资格的可验证前置条件（R1）

1. `scope=FORMAL` 仅是用户请求，不是资格证明。fixture/synthetic 不能获得真实正式资格。
2. 预检执行前就能判断的输入：来源类型、版本绑定材料、数据与协议摘要、目标与评价器兼容性。明显缺失先阻断，避免无意义调用。
3. 执行后验证实际观测：trace 是否存在且与本次 case/arm/attempt 对应、版本是否一致、题集是否完整、必要测量是否可用。
4. `trace_status`、`failure_matrix_status` 由对应验证结果生成。只有满足适用范围的检查才 PASS；未运行为 NOT_RUN/INPUT_REQUIRED，不适用为 NOT_APPLICABLE，不伪造成 PASS。
5. 故障矩阵证据绑定被测版本、协议与执行身份；不能拿另一版本的通用 CI 成功替代。
6. 正式资格材料是否需要每类故障检查由预先固定 policy 决定，不把与某一 QA 任务无关的 Agent 条件无条件强加过去。
7. 保留明确原因码与输入清单，使用户知道缺什么、如何补。正式回放若无已有完整合同，先不支持，不使用 fixture 绕过。

### 5.2 成本与缺失值（R5）

1. 采用 `value` 加 `measurement_status`/来源的结构，或等价的严格可空模型。未知不是 0，估算不是实测，明确报告的零费用才是 0。
2. token 数量缺少固定价格表时不凭空换算美元。若已有固定价格表，记录模型、币种、价格版本和覆盖范围；本轮不主动接实时价格服务。
3. 更新 CaseComparison、JSON、HTML、统计、门禁所有消费者。报告显示“未提供”，不显示 `$0.00`。
4. 配对成本统计仅使用双方成本均有效的同题观测，并公开有效配对数/总题数；不得通过丢弃失败样本美化整体结论。
5. 若 policy 要求成本门禁且测量不完整，则整体该门禁为证据不足；非成本指标可以单独展示，但不能据此声称满足完整协议。
6. baseline 成本为 0 时，定义相对变化不可计算，单列绝对差值；不除零、不让默认值产生无限收益。
7. 将统计误差与测量缺失分开，bootstrap 不能为未知成本制造有效样本。

### 5.3 引用与 Agent 指标（R5）

1. 把旧 citation_correctness 的真实含义标为预期引用覆盖率，冻结 legacy 实现版本。
2. 新版本区分引用 recall、precision；去重后计算。没有引用标签时是不可评分/不适用，不自动满分。
3. 声明“来源 ID 命中”不等于“引用支持答案主张”，后者本轮只预留指标接口，不假装已有语义 judge。
4. 保留 exact-match 用于可确定答案，并清楚标注不能代表开放问答语义质量。
5. 审查 tool_argument_validity、tool_selection_accuracy 等名称：若只是参数/序列精确匹配，就按匹配指标说明。不要为名称去实现无需求的完整工具 schema 引擎。
6. 质量 policy 按 task_type 选择真正适用的指标，不将 Agent 的缺失 citation 分数补成 1，也不让局部工具指标表上的 PASS 覆盖主门禁失败。
7. 指标版本、方向、分母、阈值和缺失策略一并固定到实验快照。禁止跑完后修改阈值使 candidate 通过。

### 5.4 验收矩阵

**S2-A：类型敏感参数与微型安全回归（R5/R13）。**

- JSON 参数比较必须区分 bool 与 number，True 不等于 1；1 与 1.0 是否等价采用明确版本规则。对象键顺序不影响结构相等，数组顺序是否重要由指标合同决定。
- 显式空 allowlist 与零预算合法，不等于字段缺失；expected tools 必须属于 allowlist 且符合预算，矛盾标签在预检拒绝。
- 固定一个小型安全边界集：正常调用、零工具、越权工具、错误参数类型、预算边界、工具返回错误、正确拒绝、错误拒绝。拒绝是否正确由 case 预期决定，不能一概把 refusal 视为失败或成功。
- 区分 budget_exhausted 与 budget_violated，安全地用尽预算不自动等于超限。
- 该集合只证明列出的工程行为，不是完整安全评估，不调用真实危险工具。

**S2-B：比较目的与执行顺序（R12）。**

1. policy 区分 qualification（绝对达标）与 non-regression（配对不退化），可同时要求，分别输出结论。
2. 工具参数、选择、预算/策略违规等阈值从 runner 常量迁入固定 policy；按指标方向配置绝对边界和可选差值容忍度。
3. 100%→95% 的复现样本可在 qualification 达标，但必须展示退步；在预注册零退化容忍规则下不得通过不退化门禁。若采用统计推断，还必须满足样本与区间要求。
4. 描述性均值、统计推断和最终正式资格分开。先复用已有适用的配对统计；不为每个新指标拼一个无依据的“显著性”标签。
5. 加入固定 seed 的平衡执行安排，记录计划和实际顺序、时间、并发、warmup/缓存设置和重试。安排交错不能保证服务缓存完全可控，未控制项写入限制。
6. 按适用指标报告逐题胜/负/平、有效配对数、缺失率、错误分类与预设类别切片。切片最低样本与是否作为门禁提前固定，事后切片仅作诊断。
7. 默认 repetitions=1。重复同题不能当成更多独立题；未来做随机性研究时按 case/group 聚合或使用明确分组统计，不能重复调用凑够样本数。
8. 新统计实现用可手算小样本和固定种子验证。超出现有能力的方法，实施前核对可靠来源与适用假设，不自行发明显著性标准。

以下验收在上述工作包和原 R1/R5 修改完成后一起执行：

- FORMAL fixture、无 trace、版本不匹配、缺故障证据各自得到准确原因，不能自动合格。
- 真实网络执行的确定性样本仍明确是工程证据，不因走 HTTP 就被识别为真实质量研究。
- 成本缺失/零费用/非法值/一侧缺失/基线为零分别覆盖。
- correct + invented 引用的 precision 下降；recall 保持其定义，二者不混淆。
- QA 与 Agent 两类任务分别覆盖合法成功、合法失败、无标签、缺输入。
- 历史 v1 文件仍能按旧合同读取，报告明确 legacy；新输出不冒用 v1 指标含义。
- 1 与 true 不被参数匹配评分视为相等；零工具合法输入可执行，越权调用仍被识别。
- 工具参数匹配 100%→95% 的达标和不退化结论不同，依据与规则在报告可见。
- 相同 seed 的安排可重放，实际执行顺序有记录；不将顺序测试宣称为已证明真实延迟公平。

## 6. S3：证据包与聚合合同

涉及：`app/product_experiments/aggregate_contract.py`、external evidence 适配模块、两个 verify 脚本、产物 writer/report、合同 fixtures 与负面测试。

### 6.1 聚合合同语义（R4）

1. 盘点当前已引用的 artifact schema、字段结构和 claim boundary 版本，建立显式解析注册表。只支持实际需要的几种，不设计无限通用框架。
2. 解析 artifact 与 reference，交叉核对 schema、题数、source identity、protocol、decision、允许与禁止声明；不能仅寻找任意一个后缀为 protocol_sha256 的字段。
3. 保留安全路径、文件大小、字节 hash 等现有检查；语义校验作为另一层，不能替代哈希。
4. 聚合 schema 使用明确允许的结构，拒绝逐题内容、未知嵌套字段和未支持的自由对象。设置尺寸/深度上限，避免把无限 JSON 当作摘要。
5. 即使结构校验通过，也不声称证明了文本中绝无私密内容。输出准确的“符合受限聚合 schema”结论，不沿用绝对的无隐私断言。
6. 在线来源/CI 核对与离线合同验证分开：离线报告没有查询远端时显示未在线核实，不能复制 pin 中的 success 当作刚刚查到的状态。
7. 旧版自由文本 claim boundary 只得到旧版有限保证；不能为兼容而自动晋级到新版严格语义通过。

### 6.2 实验包完整性（R7）

1. 完成评测的 bundle 必须有 result、report、baseline、candidate；缺输入报告按独立状态合同允许较少文件，明确没有执行。
2. result 与两个 arm 都通过版本化模型验证。交叉核对 experiment/task_type/dataset/代码身份、case_id 唯一性、数量、类别、配对集合、指标版本与状态。
3. spec 和 policy 保存脱敏快照及摘要，来源身份保存可验证引用。dataset/原始 trace 不默认发布；不能为了可复现把私有数据塞进公开证据包。
4. 权限、原始数据访问和公开摘要分别处理。公开报告不得意外暴露 prompt、答案、工具参数或内部 URL。
5. manifest 只能列出安全相对路径，拒绝重复、路径逃逸和不安全符号链接解析；保持哈希和 byte_size 一致。
6. 先在隔离 staging 位置生成完整产物，验证后再发布，避免中断留下看似完整的半包；不要覆盖已有已固定实验目录。
7. manifest 验证成功表示产物符合合同，不意味着实验质量 PASS；两个结果必须分别展示。
8. 公开导出默认采用受限摘要/脱敏模式；逐题 prompt、answer、工具参数仅在明确的受控本地/授权导出模式提供。保留私有原始材料摘要和访问方式，不删除原始数据伪称完全公开可复现。
9. execution 身份、输入投影版本、限额、失败分类、比较目的和实际执行顺序进入证据合同。导出用冻结的执行快照，不读取后来改变的配置。

### 6.3 必须拒绝的负面材料

- 已知 pin 对应文件被改但 hash 没更新。
- 新 pin/hash 全部正确，但 schema 未知、case_count 与引用不一致。
- decision/protocol/source/claim boundary 不一致。
- 加入 case_results/prompt 或未知嵌套结构。
- 从文件和 manifest 中同时删除 baseline 或 candidate。
- 重复 case_id、两组题目错配、result 与 arm 数量/任务类型不一致。
- manifest 路径逃逸、指向目录外的链接、文件缺失、大小不符。
- 报告包含待脱敏的测试秘密标记。

S3 验收：上述材料按准确原因失败；现有合法历史材料仍获得其实际对应的旧版保证，新版合法材料获得新版保证。绝不修改历史字节来让测试通过。

## 7. S4：把产品入口接入现有持久 Run/Job

这是本轮最大的实现部分，必须拆成小关卡。现有 `AgentRegressionComparison` 是完成后的不可变比较报告，不是可恢复的实验控制记录；不能直接把它改成任意可变状态容器。

### 7.1 最小架构

用户 → 经过鉴权的实验提交 API → 一个实验控制记录 + baseline/candidate 两个现有 Run → 现有 Job/Worker/Lease/Outbox → 共享评分与比较 → 可重复导出的不可变报告。

推荐新增一个最小、租户隔离的实验控制记录，关联现有两个 Run。不新增调度循环，不把运行进度只保存在 CLI 内存。

建议记录：tenant_id、experiment_id、客户端幂等键、规范化请求 hash、固定 spec/policy/dataset 与组件身份、两组 run_id、取消意图、最终结果 artifact 引用、创建时间和并发控制版本。进度优先由已有 Run 状态推导，避免多份计数漂移。

### 7.2 S4-A：数据映射与事务设计

1. 将 product case 的 prompt/reference/tool expectations 显式转换成现有 DatasetCase 的 question/expected_answer/metadata；保存原始输入与规范化 dataset 两种摘要及映射版本，不能假装转换前后字节相同。
2. 两组必须引用同一个不可变 dataset version。target 与 evaluator 使用注册组件，服务端不接受任意用户提供的外部 URL 绕过 registry。
3. API 与 CLI 都只引用 secret 名称/服务端注册 target，不接收或存储明文 token。
4. 外部 artifact 读取与校验在数据库写事务外完成；在同一个数据库事务里插入实验关联、两组 Run 和 Jobs。
5. 当前 `create_or_replay` 自己开启事务。应抽取可复用的“已有 session 中插入 Run/Jobs”内部函数，原入口继续调用该函数；不能仅在两个会自行提交的方法外套 begin 就声称原子性。
6. 并发唯一约束：同租户同幂等键同请求返回同一实验；不同请求返回冲突；不同租户互不影响。
7. 新表使用复合外键确保两个 Run 的 tenant 与父记录一致，补索引与 RLS。沿用并核对现有锁顺序，不在无证据时优化 scheduler 锁。
8. 迁移以增量方式进行，旧 Run 继续有效；不回填虚构的实验身份。仅在隔离测试库演练 downgrade，生产回退以代码关闭入口/前向修复为主。
9. 两组与重试共享 S1 固定的实验限额，不能每组各领取一份总预算。必要计数采用事务/唯一约束；没有可靠费用预留前不提供硬美元预算承诺。
10. 评测标签虽可保存在 DatasetCase.metadata 供 worker 使用，对外请求仍通过 S1 的同一输入投影；不能在 durable 路径再次整包转发。

验收：故障注入到第一组插入之后，不得留下可被 worker 执行的半个实验；数据库事务回滚后无孤立 Run/Jobs。并发重复提交只产生一对 Run。

### 7.3 S4-B：执行与评分接入

1. 在现有 worker evaluator registry 中新增必要的薄适配器，调用 S1/S2 的共用合同和纯评分逻辑。
2. 不另写一套 tool error、成本或 citation 公式；本地模式与 worker 模式对相同输入输出应一致。
3. 将完整但脱敏/受权限保护的归一化执行产物绑定 run/job/attempt/版本；沿用现有 artifact ownership 和 stale attempt fencing。
4. 重试保留每次 attempt 的事实，最终质量只使用被接受的有效结果，不能把旧结果混入新结果。
5. 质量失败与基础设施失败分开：合法得到差答案一般不重试到“碰巧通过”；timeout/传输失败是否重试由固定策略决定。
6. 比较与导出读取冻结的有效结果集合，允许重算/重导出，不再次调用被测服务。记录比较算法和 policy 版本。
7. 尽量复用现有 Agent 比较/证据持久化能力；若语义不一致，写薄适配或独立产品快照，不改写历史 Agent 比较数据。
8. provider 接收真实 Run/Job/attempt 身份，不再从可读 label 重建。错误分类和缺测状态随有效 attempt 保存，local/durable 使用相同含义。

验收：同一受控 response 在 local 与 durable 模式的结果、缺失状态、指标与门禁一致；两个模式都能处理合法失败。

### 7.4 S4-C：API、CLI 与取消

推荐接口：提交、查询、取消、导出实验。确切 URL 与 CLI 子命令在 S4-A 后写入 OpenAPI 和帮助信息；本文件不是宣称这些命令已存在。

- local 模式继续保留快速 demo，不强迫简单样例启动数据库。
- durable 模式通过 API 提交，返回稳定 experiment_id；支持查询/等待和按 ID 导出。
- 客户端退出不取消服务端任务；再次按 ID 查询即可继续等待。等待超时输出恢复命令与实际状态。
- 显式取消写入持久意图，再调用现有取消机制；重复取消幂等。无法中止已经发生的外部副作用时明确记录，不伪称撤销。
- 查询、取消、导出都做租户校验，跨租户对象按现有隐藏存在性约定处理。
- 第一版先采用查询/导出时的幂等聚合，不为自动生成报告新增常驻进程。导出失败可重试，不重跑评测。

S4 验收：不能仅通过 SQL 预置 Run/Job 完成“端到端”测试。至少一条测试必须从公开的鉴权 API 提交，走真实 worker 执行后通过公开导出接口获得报告。

## 8. S5：真实进程故障、隔离与 CI 总验收

### 8.1 测试分层

| 层级 | 要证明的内容 | 不得冒充的内容 |
| --- | --- | --- |
| 单元 | 合同、公式、缺失值、状态、路径验证 | 真实数据库并发 |
| API/服务集成 | 身份、幂等、事务、Run 关联 | worker 进程死亡恢复 |
| PostgreSQL 并发 | 重复提交、租约隔离、取消与写入竞争 | 外部工具 exactly-once |
| HTTP + worker + DB + artifact | 完整产品输入输出与实际恢复 | 真实模型质量 A/B |
| 历史合同回归 | 旧证据按旧版本仍可审查 | 历史结果自动满足新标准 |

### 8.2 故障矩阵

| 场景 | 注入位置 | 必须观察的结果 |
| --- | --- | --- |
| 两组创建中断 | 第一组写入后、提交前 | 事务回滚，无半个可运行实验 |
| worker 取到任务后退出 | claim 后、执行前 | lease 到期后被恢复；已完成任务不重复执行 |
| 服务已处理但 worker 未持久化 | HTTP 完成后、结果提交前 | 可能发生外部重试；内部只接受一个有效结果，并诚实记录副作用风险 |
| stale worker 回来写入 | 新 attempt 已生效后 | 旧版本写入拒绝，不覆盖新结果 |
| 提交响应丢失 | 数据库提交后、客户端收到前 | 同幂等键重试返回原实验，不重复创建 |
| 取消与完成竞争 | 同一任务并发取消/提交 | 遵循明确终态规则，不出现取消后伪造成功 |
| 两个导出者并发 | 读取完成 Run 后 | 相同冻结输入对应同一逻辑结果，无半包或互相覆盖 |
| 一组失败/缺题 | 有效结果不足时 | 不只取成功交集宣布完整 PASS |
| artifact 存储临时失败 | 结果写入或导出时 | 可重试/可诊断；数据库与 blob 不形成无记录的成功假象 |
| API key 跨租户访问 | 查询/取消/导出 | 无数据和对象存在性越权 |
| CI 进程收到质量 FAIL | CLI 结束时 | 非零退出码真实传播 |
| 标签混入 metadata | 实际请求构建/发送 | gold/fixture/期望标签不外发，公共上下文仍可用 |
| 限额/慢流 | 输入、读取、任务窗口、总 deadline | 有界拒绝/终止并释放资源，不靠耗尽内存验证 |
| 新执行/重复提交/恢复 | 提交、重放、retry | 各身份符合合同，改变输入不混用旧执行 |
| 零工具/参数类型 | Agent 预检与评分 | 合法任务不误拒，true 与 1 不误判相等 |
| 达标但专项退步 | 相同配对样本 | 达标和不退化结论分开，原因可解释 |

### 8.3 真实 HTTP 测试的安全边界

使用隔离环境中的确定性测试服务，测试成功、错误工具调用、预算耗尽、缺字段与延迟。由于生产 target 会拒绝私网地址，测试只在测试进程注入受控网络 fixture；不得通过放开生产 SSRF 策略来图方便。

真实 HTTP 传输验证与生产 URL/DNS/allowlist 策略验证分别保留证据。若不能在不削弱生产策略的前提下完成某项测试，记录限制并调整测试基础设施，不宣称已经覆盖。

### 8.4 CI 修改

- 保留现有锁文件、ruff、mypy、数据库并发、MinIO、迁移和 Compose 就绪/硬化检查，不通过删除难测项变绿。
- 增加新单元/CLI 负例、product durable HTTP E2E、数据库迁移和租户测试；该执行的集成项不允许因缺 env 静默 skip。

## 13. 后续需求驱动的 T1–T4：有完整方案，但不默认全部实施

以下工作在交付 A/B/C 完成后再评估；不是让当前修复一直无法结束的新要求。默认选择最能解决真实使用问题的一项，先完成再决定下一项。

### 13.1 T1：低成本验证非 RAG 扩展性

触发：有实际结构化提取/分类需求，或者确实需要用第二类业务任务验证扩展接口。

范围：优先只选一个结构化 JSON 输出任务 pack，包含版本化 case schema、确定性字段/类型/枚举检查、合法/缺字段/多字段/错误类型样例与同一报告入口。不支持在配置中执行任意 Python，不接满流行框架。

步骤：固定使用者与示例 → 确认现有 QA/Agent 是否已足够 → 只增加必要 case adapter/evaluator → 跑相同 local/durable 合同 → 展示字段级原因 → 更新能力矩阵。

验收：不改租约/调度核心即可接入；未知任务显式拒绝；既有 QA/Agent 结果不变。没有真实需求时先停在扩展文档，不为“通用平台”继续堆类别。

### 13.2 T2：性能归因与调用开销

触发：有明确容量目标或可复现的慢问题。HTTP/client、数据库、worker 和导出开销分开，不先假定 scheduler 是根因。

步骤：

1. 固定代码/环境/数据/租户分布与口径，分别测 queue wait、数据库等待、目标调用、持久化和报告生成。
2. 对已有 4→8 worker 负扩展性做控制变量与重复测量，记录实际完成量、失败/重试、CPU/内存/数据库等待，不偷换成另一种负载。
3. 选择一个有证据的瓶颈作最小修改。连接复用、分批读取、聚合导出可作为候选，但必须保持 DNS/peer/目标凭据与租户隔离。
4. 同协议比较前后，并重跑公平性、过期写入和取消回归。吞吐上涨但正确性下降不能接受。

验收：口径一致的原始摘要、归因说明、无正确性回归；改善不成立就保留负结果，不升级容量声明。完成一个瓶颈后重新判断，不无限微调。

### 13.3 T3：公开多租户运行资格

触发：明确要公开部署或让其他用户长期使用。开发 Compose 不作为生产权限证明。

工作顺序：独立迁移/运行数据库角色 → 实际运行账号的 RLS/最小权限 → 提交配额/速率限制/过载响应 → API key 生命周期与部署秘密管理 → retention/存储预算 → 备份恢复演练 → 依赖/镜像安全检查与升级策略 → 可操作的告警。

复用已有鉴权、低基数指标、outbox cleanup 和隔离测试。提交配额先明确场景与公平性，不顺带创建复杂计费系统。任何清理仅在明确授权范围执行，不自动删除生产数据或降级数据库。

验收：实际部署身份通过越权测试，备份在隔离环境恢复且证据可核对，限额生效，升级失败能保留数据回退。只声称指定部署范围通过验收，不笼统写“绝对生产级”。

### 13.4 T4：真实质量研究与人评

触发：有合格数据、真实目标版本、清晰研究问题，以及用户授权的预算和人审资源。

步骤：冻结研究问题与 policy → 检查独立题数/类别/来源 → 固定版本、请求映射、指标、成本来源 → 控制并记录顺序/缓存/随机性 → 真实执行 → 合法配对统计 → 盲审/分歧处理 → 发布包含负结果与限制的报告。

重复同题采用明确的 case/group 统计单位，不能把重复调用计为更多独立题；主要指标和探索性切片预先区分。方法超出现有实现时先查证适用性，不临时发明显著性规则。

验收：工程材料、统计、人审和正式声明对应；资料不足仍 INPUT_REQUIRED。完成研究不保证 candidate 获胜，没有输入时不阻塞本轮工程交付，不要求用户为简历强行付费。

### 13.5 暂不做

新前端大屏、全框架接入、Kubernetes/多集群、插件商城、自建通用 judge 平台、为了好看重生成历史 PASS，均不在默认范围。若出现具体需求，再列出价值、成本、风险和验收条件。

默认结束点是“处理 R1–R13、贯通一条真实可恢复流程、留下证据并完成约定同步”，不包含无条件执行 T1–T4。新发现若只是推测，先记录并进行有界验证，不自动扩大任务。
