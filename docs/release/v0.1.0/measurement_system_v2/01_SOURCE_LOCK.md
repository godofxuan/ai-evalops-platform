## Behavioral paths

The deterministic source-lock helper fails the experiment if any path below changes between the
code lock and execution SHA:

```text
app/
scripts/
alembic/
deploy/
.python-version
alembic.ini
pyproject.toml
uv.lock
```

`alembic/` and `alembic.ini` bind database schema/migration behavior. `deploy/` binds PostgreSQL and
Redis image/topology settings. `.python-version`, `pyproject.toml` and `uv.lock` bind interpreter and
dependency behavior. The benchmark fixture is generated by the locked script; repository `data/`
is not consumed by this benchmark.

`Dockerfile` was considered and excluded because the qualification runs the locked uv environment
directly on the GitHub runner and starts only the database services from `deploy/compose.yaml`; it
does not build or execute the application image. `.env.example`, README files and `.dockerignore`
are documentation/build-context examples and do not determine this workflow's executed benchmark.

Documentation, immutable evidence directories and the dedicated trigger/workflow may be added after
the code lock. They do not bypass identity checks: the workflow itself is fixed by `GITHUB_SHA`, the
three preregistration files must predate the trigger, and every run row independently binds source,
measurement-code and workflow-run identity.

## Post-lock allowance and race-safe preservation

After this code lock, only preregistration/source-contract documentation, workflow/trigger and new
evidence/report documentation may change before execution. Evidence preservation must use a
separate job with write permission, require the remote branch tip to equal the trigger SHA, create a
normal child commit, and perform a non-force fast-forward push. A changed remote tip yields
`PRESERVATION_CONFLICT`; it must not be rebased, merged or overwritten silently.
